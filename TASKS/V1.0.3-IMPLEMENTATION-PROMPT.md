## Scope: target version 1.0.3

### A. Windows Host and Recovery
- Analyze the actual Host startup, Recovery Agent/supervisor, process detection, task scheduling and IPC/relay behavior.
- Repair Recovery so that the existing Recovery button in Windows Viewer works reliably.
- Preserve the current Recovery logic and intended behavior; fix the actual failure rather than replacing the mechanism.
- Ensure the Recovery action works with the installed Host and Recovery Agent, reports a real result, and does not silently fail.
- Do not introduce an unnecessary backup/restore system. Do not require administrator privileges unless the exact Windows operation genuinely requires them; if elevation is required, identify the operation and handle it explicitly.
- Check startup/task-scheduler behavior for the intended user scope and ensure no duplicate process/agent loops.
- Verify the real process path and launch arguments. Preserve existing working Block/Unblock behavior.

### B. Windows Viewer
- Repair the Recovery button and its request/response/UI state.
- Audit every existing button, menu item, command and connection state; fix regressions without removing features.
- Support multiple monitors. Show monitor choices such as Screen 1, Screen 2, etc., based on monitor information actually supplied by Host.
- Allow selecting and viewing each monitor independently without dropping the Host connection.
- Ensure remote-control coordinates map correctly to the selected monitor and displayed image, including scaling/letterboxing.
- Preserve the existing relay protocol and connection lifecycle.

### C. Android Viewer — functional parity
Make Android Viewer a real mobile counterpart to Windows Viewer, not a reduced demo.

Implement and verify, using only protocol actions confirmed in the existing Host/Windows Viewer:
- host discovery/list and selection
- connection status and reconnect behavior
- remote screen viewing
- multiple monitor selection and switching
- remote input/control, including correct coordinate mapping
- Recovery action and clear result/error state
- Block and Unblock controls
- all other tools and commands that exist in Windows Viewer and are supported by Host
- appropriate loading, disabled, error, timeout and disconnected states

Remove the user-facing Relay URL input. Keep the endpoint in internal app configuration. Do not expose a field the user must manually populate. Preserve the existing endpoint unless source/configuration evidence requires a change.

Implement reliable reconnect with bounded backoff, lifecycle-aware socket cleanup, heartbeat only if the established protocol requires it, and a clear list of available Hosts. Do not auto-select an arbitrary Host when the user has multiple choices; make discovery and selection predictable.

### D. Android UI and input
- Support portrait and landscape; remove fixed landscape-only behavior.
- Adapt to phones and tablets and different screen sizes/densities.
- Ensure controls remain reachable and readable in portrait and landscape.
- Use a responsive layout rather than hardcoded dimensions.
- Correctly account for image scaling, aspect ratio, crop/fit behavior and letterboxing when mapping touch coordinates to Host screen coordinates.
- Handle touch down/move/up/cancel, pointer identity and control release on disconnect/background so input cannot remain stuck.
- Support monitor switching without reconnecting the Host session where protocol allows.

### E. Protocol and compatibility
- Treat the existing Windows Host and Viewer implementation as the protocol specification.
- Before adding an Android command, identify the exact Windows source method and corresponding Host handler.
- Do not change relay message names, separators, binary frame headers, room/role semantics, heartbeat rules or endpoint unless necessary and proven compatible.
- Maintain backward compatibility with existing Host versions wherever possible.
- Do not log credentials, private data or screen contents.
